# Decision log

Lightweight project decision log (ADR-lite). Rules:

1. **Every non-obvious decision is recorded here in the same PR that
   implements it** — same law as the sync rule in AGENTS.md.
2. Each entry links its trail: ticket, commit and/or doc section.
3. Entries are never deleted; if a decision is reversed, a new entry is
   added referencing the old one.

Format: `## D-NNN · date · title (ticket)` with **Decision / Alternatives /
Why / Trail**.

> Product documents (`reglas-y-especificacion.md`, `brief-tecnico.md`) are
> written in Spanish for the neighborhood association — see D-014.

## D-031 · 2026-07-06 · Canvas geodata retired at LCHP-13; seeds convert via affine transform (LCHP-4)

**Decision:** the MapLibre + OSM raster stack is confirmed for the MVP with spike evidence (brief §21, now verified). The prototype's `lalatina-geo` canvas geometry (1000×527 space, D-016) **cannot overlay real tiles** — a best-fit affine transform (9 plaza anchors, Nominatim-geocoded) leaves 4–39 m residuals (RMS ~25 m), visibly cutting through buildings at z17 — so it is retired when MapLibre lands: OSM tiles already draw the streets. Canvas-space sighting seeds are converted once via the fitted affine transform (documented in §21; acceptable because the product shows approximate locations by design) or re-seeded by hand; the map frame uses the fitted bbox `[[-3.7173, 40.4093], [-3.7068, 40.4138]]`. The §21 `tileProvider` sketch is upgraded to a discriminated union (`kind: 'raster' | 'vector'`) with a `buildMapStyle()` that was exercised verbatim in the spike page.
**Alternatives:** overlaying the canvas streets on MapLibre via the affine transform (rejected: visible misalignment, and redundant — tiles already render streets) · re-seeding every mock sighting by hand (kept as fallback; more work, no accuracy need) · keeping nullable `styleUrl`/`rasterTiles` fields in the config (rejected: orphan fields, worse typing).
**Why:** the spike's numbers say the transform is fine for approximate points but not for line geometry at high zoom; retiring the canvas layer removes an entire dataset instead of maintaining a lossy projection of it.
**Trail:** LCHP-4 · brief-tecnico.md §21–§23 · D-016 · LCHP-13 (implementer).

## D-032 · 2026-07-06 · Anonymous sightings allowed in the MVP; quota enforced by Postgres trigger (LCHP-3)

**Decision:** anonymous users CAN create sightings from their first submission (no magic link gate); the per-day quota (2/day anonymous, 5/day registered, brief §30) is enforced in Postgres with a `BEFORE INSERT` trigger calling a `security definer` function that counts the user's rows for the current day and picks the quota from the JWT's `is_anonymous` claim. The Edge Function may pre-check for friendlier errors, but the trigger is the source of truth.
**Alternatives:** require magic link from the first submission (kills first-touch participation in a neighborhood pilot; unnecessary — the upgrade preserves `user.id`, so nothing is lost by starting anonymous) · enforce the quota only in the Edge Function (bypassable via direct PostgREST; weaker guarantee than the data layer).
**Why:** verified against the real free-tier project (LCHP-3 spike): real anonymous sessions work (`is_anonymous=true` claim, 1 h JWT + refresh, permanent `auth.users` row), the anonymous→registered upgrade keeps the same `user.id` end-to-end (magic-link email followed on a local stack), RLS policies distinguish both types via the claim, and the trigger blocked the 3rd anonymous / 6th registered insert of the day in live tests.
**Trail:** LCHP-3 · brief §16, §30, §32 (enmiendas 2026-07-06) · PR of this spike.

## D-034 · 2026-07-06 · State fields are text + CHECK, not Postgres enums (LCHP-10)

**Decision:** every state/vocabulary column (`sightings.moderation_status`, `sightings.confidence`, `profiles.role`, `point_events.type`, `verifications.type/status`, `reports.reason/status`, `species.rarity`) is `text` with a `CHECK (col IN (…))` constraint instead of a native enum type.
**Alternatives:** `CREATE TYPE … AS ENUM` (native enums) · unconstrained text.
**Why:** the schema is deliberately created in full as an escape valve (AGENTS.md §ceiling), so vocabularies WILL evolve; changing a CHECK is a drop+add in one migration, while enums need `ALTER TYPE` ceremony (no removal, ordering quirks, in-transaction limits on older PG). Unconstrained text loses data integrity for zero gain.
**Known trade-off (Codex adversarial review, LCHP-10):** `supabase gen types` emits literal unions only for native enums — CHECK-backed columns come out as plain `string` in `src/types/database.ts`. Accepted: the app never consumes the generated row types directly; screens depend on hand-authored view-model types through the service layer (D-007), which keep the literal unions, and state transitions are created exclusively server-side (brief §15, LCHP-12/15) where the CHECK is the enforcement. If M3+ wiring ever exposes the widened fields to app code, narrow them there (e.g. a typed override of `Database`), not by migrating to enums.

## D-038 · 2026-07-06 · Verifications: direct client INSERT under RLS; consolidation by server-side trigger (LCHP-11, affects LCHP-15)

Whether a confirmation COUNTS is decided server-side: while `app_config.verification_requires_registration = 'true'` (default, fails closed on a missing key), an anonymous confirmation is stored as **provisional support** — `status` stays `pending`, it adds nothing to the threshold and mints no points. When its author registers (same `auth.users` row, LCHP-3), the `on_auth_user_registered` trigger **activates it retroactively**: it counts toward `validation_threshold` (possibly validating the sighting then) and collects its +5. Consolidation lives in `private.consolidate_sighting()`: sighting row lock (`FOR UPDATE`) + atomic `UPDATE … WHERE moderation_status = 'pending'` as THE concurrency boundary (the binding LCHP-11 contract — proven with a real parallel race at threshold 1: one 201, one 403, exactly one +10). On a successful transition, **every** counting confirming verifier earns +5 (David's call: not only the one who tipped the threshold — matches brief §15 and doesn't punish early verifiers), guarded per-row by `verifications.points_awarded`; the author's +10 is guarded by `sightings.points_awarded`; `profiles.total_points/weekly_points` caches update in the same transaction. Flipping the switch to `'false'` (an UPDATE, no deploy) makes anonymous confirmations count fully — the pilot escape valve — and an `app_config` trigger consolidates the provisional confirmations ALREADY stored at that moment (Codex round 2, HIGH: they would otherwise stay inert).
**Alternatives:** registered-only verification (D-038 as written — walls out the 100%-privacy neighbor; every step of the UX research pointed away from walls) · full anonymous verification (rejected: reopens the incognito self-validation HIGH from LCHP-11 — no studied platform lets an identity-free action flip rewarded state) · threshold variants (≥1 registered among N) — more complex, weaker than deferral.
**Why:** David re-opened D-038's premise during LCHP-15 kickoff wanting privacy-first neighbors to participate. Research across 7 platforms (iNaturalist, eBird, Zooniverse, OSM Notes, FixMyStreet, Waze, Wikipedia) found the two transferable patterns this design composes: OSM's provisional-signal ("should be independently verified") and e-commerce deferred credit (guest checkout → claim on signup). ## D-057 · 2026-07-10 · Map pin popover paint order fixed with a local z-index, not a shared-sprite change (LCHP-32)

**Decision:** the map pin popover (`MapPage.tsx`) gets `position: relative; z-index: 1`. Root cause of David's bug: on a short viewport the map screen is a non-scrolling flex column (`.screen` + inline `overflow: hidden`), and the «Cerca de ti» list is `flex: 0 0 auto` with `min-height: 168` so it refuses to yield space; the top pad (`flex: 1 1 auto; min-height: 0`) is squeezed below its content and the popover — its last child — overflows the pad's bottom edge, geometrically overlapping the list. The list is a *later* sibling in the same root stacking context and its `PixelSprite` cells are absolutely positioned, so by CSS paint order a list sprite (or the list header/chip) painted over the popover. A positive z-index lifts the whole popover into the stacking context's positive layer, above the list's in-flow and positioned content. The geometric overlap itself is left as-is: the popover is a transient detail panel meant to sit *over* the list, so covering the list's top is correct — only the paint order was wrong.
**Alternatives:** `isolation: isolate` alone (creates a stacking context but for a non-positioned element it paints in the in-flow band, so a *later* non-positioned sibling still wins — insufficient here) · touching the shared `PixelSprite` to stop using an absolutely-positioned box-shadow cell (wide blast radius: it renders every sprite on every screen — legend, Pokédex, ranking, profile — and the box-shadow technique is the whole point of the prototype-ported renderer) · restructuring the flex layout so the popover can never overflow (larger change, and the overlay-over-list behavior is intended). The full-screen overlays (`VerifyModal`, evidence overlay: `position: absolute; inset: 0; z-index: 80`) were audited and are already safe — they establish their own stacking context and cover the screen.
**Why:** minimal, local, and idiomatic; the fix lives on the one element that was wrong and leaves the shared renderer and the intended layout untouched. Verified via the Playwright visual loop at a constrained mobile viewport (412×720, reduced-motion — the settled/real-device state): before, the list bled over «Ver evidencia»; after, the popover is an opaque panel on top.

## D-059 · 2026-10-08 · Basemap: OpenFreeMap vector tiles with a vendored chispera style (LCHP-33; amends D-001/D-031, retires D-045)

**Decision:** the basemap switches from OSM's public raster tiles to **OpenFreeMap vector tiles** (OpenMapTiles schema, tilejson `https://tiles.openfreemap.org/planet`, OpenFreeMap glyphs) rendered with a **vendored style**, `src/components/map/styles/chispera.ts`, generated by `scripts/build-map-style.mjs [palette]` from a **committed snapshot** of OpenFreeMap's `positron` (`scripts/positron.snapshot.json`, fetched 2026-10-08; `--refresh` re-downloads it for review). Changes vs positron: the chispera palette on the layers this map can show (aeroway, glacier and ice-shelf colours stay upstream — nothing inside `maxBounds` draws them), labels `coalesce(name:es, name:latin, name)`, the three road-shield layers and `airport` dropped (they need positron's sprite sheet; La Latina has none), the low-zoom `ne2_shaded` relief source dropped (unreachable inside `maxBounds`), place-label `icon-*` properties dropped, fountain/pond labels (`water_name_point_label`) shrunk from 14 px to 10–12 px because they out-shouted street names, and positron's `["linear", 1]` typo in `boundary_3` corrected. The style is a **typed TS module** (`export const chisperaStyle: StyleSpecification = {…}`), not JSON: the compiler checks every layer against MapLibre's spec and no cast is needed (MapLibre's own `validateStyleMin` also returns zero errors). `tileProvider.ts` shrinks to one object, `{ id, style }` (`style: StyleSpecification | string`), read by both maps; the raster branch and `buildMapStyle()` from the LCHP-4 spike are gone and **no raster fallback is kept** (David, 2026-10-08: it was a path nobody ran, dragging a style-builder branch, a per-provider flag and their tests; going back to OSM raster is a small revert and its tile policy stays documented in brief §21). The D-045 CSS canvas filter and both multiply veils are deleted.
**Licences and credits (David's call, 2026-10-08, after reading the licences):** positron is BSD-3 (code) + CC-BY 4.0 (design, derived from CartoDB Basemaps by Stamen/Paul Norman, CC-BY 3.0), via openfreemap-styles (MIT). (1) The upstream `LICENSE.md` is vendored verbatim as `src/components/map/styles/POSITRON-LICENSE.md` and the module header keeps the copyright lines and points to it — BSD-3 source retention; the snapshot we generate from is OpenFreeMap's adaptation, so that repo's licence file (MIT, Copyright (c) 2023 Zsolt Ero) is vendored too as `OPENFREEMAP-STYLES-LICENSE.md` and named in the header. (2) A **credits page**, `/perfil/creditos` «Créditos y licencias» (nested under Perfil so its tab stays active), linked from the Perfil footer, shows the design credit with the CC-BY link and both licence texts (imported from the vendored files, so page and source cannot drift) — BSD-3 "binary form" reproduction, and CC-BY's "reasonably accessible from maps based on this style"; the licence says the design credit "needs not to be provided on map images", so it is **not** in the map's attribution control. (3) The **data credit** stays on the map: OpenMapTiles requires its credit "in the corner of the map" and the OSM Foundation guidelines require OpenStreetMap's credit in a corner, allowing it to fold on map interaction or after five seconds as long as it stays findable. `attribution.ts` therefore adds MapLibre's compact control — open on load, never folded at start — and folds it to the (i) button after 5 s or on the first user move (drag, pinch, wheel or double-tap; MapLibre alone folds only on drag; a programmatic recenter does not fold). The five seconds count **from the moment the credit is on screen, and only in a visible tab**: the text arrives with the tile metadata, and with the clock started at map construction a slow network left it visible for 0.4–1.9 s (measured by the Opus seat in round 3); hiding the tab stops the clock and it restarts in full on return. The fold happens **once** — a credit the user reopens with (i) is never folded again by our code — and a single wheel notch counts as a user move even though MapLibre reports it without an original event. OpenMapTiles' text has no folding clause; reading "corner of the map" as satisfied by the standard compact control is our interpretation, and MapLibre's own docs advise not collapsing a credit that fits — folding on interaction only (no timer) is the more conservative variant and a one-line change if ever wanted.
**Invariants pinned by tests:** every layer's `source-layer` is on an allowlist (no `poi`, `housenumber`, `mountain_peak`, `aerodrome_label`…), and **text may only come from `transportation_name`, `water_name`, `waterway` and `place`** — a label on `building`, `landuse` or `park` would name a venue (golden rule, D-046); a single OpenFreeMap source; no key/token in the style; the exact Spanish-first `text-field` on every named layer; no sprite; the fold (the literal 5000 ms; not before five seconds of the credit being shown; clock not started while the credit is empty, in a hidden tab, or by `load`; hidden time not counted; at once on a user move or a wheel notch, not on a programmatic move; a reopened credit left alone; nothing after cleanup; the control created compact); the credits page content, its link from Perfil and the active Perfil tab.
**Weight trade-off (measured by the Opus review seat, built app, 412×892@3):** first load fetches 4 z14 vector tiles ≈ 1.5 MB gzip (2.5 MB decoded) + 3 glyph ranges + tilejson ≈ 1.6–1.7 MB, versus 284 KB for 9 z16 raster PNGs on `main` (577 KB after load+zoom+drag); after that the bounded map needs at most 9 z14 cells, served with `max-age` of ten years, so repeat visits are near-free and the service worker (LCHP-17) can keep them. Privacy upside: tile requests now reveal only the z14 cell (~1.7×1.3 km) around the viewport instead of z16–z19 cells. **Caching stance for LCHP-17:** tiles, glyphs and the style may be runtime-cached (stale-while-revalidate); the basemap is never precached — for size and because OpenFreeMap's ToS forbids automated bulk collection; if a CSP lands, `tiles.openfreemap.org` in `connect-src`/`img-src`, `worker-src 'self' blob:`, and the CSP only on HTML pages (a cached worker file keeps a stale CSP for days — Alcorqueando, 2026-10-05).
**Alternatives:** keep OSM raster + CSS tint (D-045: blurry on retina, no label control, strict usage policy, house numbers visible from z17, the "embedded Google Maps" look) · keyed vector providers from brief §22 option B (MapTiler, Stadia, Jawg…: account + key + capped free tier) · load positron by URL and patch paint/layout at runtime after `load` (Alcorqueando's approach: no vendored diff, depends on upstream style edits, not type-checked) · vendor as `.json` (needs an `as unknown as StyleSpecification` cast the codebase forbids, and loses compile-time validation) · own tiles on R2/Pages (§22 option C: kept as the post-MVP escape hatch — OpenFreeMap publishes full-planet dumps only, so this means cutting a La Latina extract with planetiler/Geofabrik and serving z/x/y; `// TODO(post-mvp)` in `tileProvider.ts`) · showing the Positron design credit inside the attribution control (tried in review round 1: it grew the control from 351×24 to 360×44 at 412 px wide and to 268×64 — 28% of the map card — at 320 px, for a credit the licence does not require on the map) · a `park_label` layer for park names (tried in round 1 and removed: in OpenMapTiles the `park` layer holds protected and heritage areas — inside our bounds it labelled a heritage wall and an institutional building, not Las Vistillas; the names neighbours use live in `poi`, which the golden rule excludes).
**Why:** the July choice was made by elimination — every vector provider evaluated needed an account; OpenFreeMap (no registration, no key, no stated limits, commercial use allowed, attribution required, as-is service that may be discontinued without notice, no SLA — <https://openfreemap.org/tos/>) was never on the list. It satisfies the exact constraint that picked raster while removing its downsides, and Alcorqueando has run on it since 2026-10. Vendoring makes the look deterministic and reviewable; typing it makes the style a checked artifact rather than a blob; committing the generator and its input keeps a palette change a one-line, reproducible command. **Known loss vs raster OSM:** no venue, metro, church or park labels — the basemap names streets, water and neighbourhoods only (plazas appear where they are streets in `transportation_name`). **Colour:** four candidates (pergamino · papel · tierra · verde) screenshotted on the same `/mapa` frame via the visual loop (same method as D-045); David picked **`papel`** on 2026-10-08 from the side-by-side page (lightest ground, white roads — the most contrast under the pixel sprites); the other three stay in the generator.

## D-064 · 2026-10-09 · Workflow: a review loop has a budget set at kickoff; a PR that changes what the user sees shows it (amends D-033)

**Decision (David, 2026-10-09):** two rules join the workflow in `AGENTS.md`.
1. **The number of review rounds is decided at the start of a ticket, from its complexity**, and written in the kickoff comment. When it is spent without a clean verdict the loop stops and the open findings go to David with a recommendation each. Working scale: none or one round for docs and trivial changes, two for a small contained change, three or four for a substantial or stateful one or anything in the security-critical zone.
2. **A PR with a visible change carries screenshots in its body**, before/after pairs with the same fixture data and viewport. They are published on a `pr-assets` branch and linked by commit, so `main` carries no images.
**Alternatives:** review until every seat approves (LCHP-34 ran thirteen rounds over three PRs, each fix surfacing a narrower finding on controls most users never see) · a flat cap of two for everything (what was applied to LCHP-41 and at first to LCHP-35 by over-reading what David had said about one loop; a rewrite of the map controller is not a two-round change) · screenshots only in the chat with the agent (David cannot share them, and reviews by eye on his phone) · images committed to `main` (permanent weight in the history for something read once).
**Why:** the review exists to find defects, not to converge on zero remarks; past a point each round costs more than what it finds, and only the owner can say where that point is for a given change. And a visual change is judged by looking: the before/after pair of LCHP-41 settled in seconds what a pixel-difference percentage had not.
**Trail:** LCHP-35 (first PR under both rules; budget three) · `AGENTS.md` «Linear and GitHub — how we work».
